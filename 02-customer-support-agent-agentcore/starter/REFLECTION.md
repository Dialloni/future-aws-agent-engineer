# Reflection

**Design decision.** For loyalty discounts I chose to run the arithmetic in the AgentCore Code Interpreter instead of letting Nova Lite compute it. The rules have several dependent steps: points are redeemed in blocks of 500, capped at 50% of the order, and the tier discount applies to the subtotal after points. LLMs are unreliable at this kind of multi-step math, so the tool builds a self-contained Python string and executes it with clearContext=True, giving a deterministic, auditable result (Gold, 4,250 points, $150 order: 4,000 points redeemed, $99.00 final, 250 remaining). A tier-only fallback still answers the customer if the sandbox is unavailable.

**Challenge.** My first order-tracker Gateway target went to FAILED. The status reason said the exported OpenAPI spec was missing "responses" for all three GET operations. I had built the REST API from the terminal, and unlike the console, the CLI does not add a default 200 method response. I added a 200 method response to each GET, redeployed the prod stage, confirmed the export with get-export, and recreated the target; all six tools then appeared in tools/list. A second issue was IAM: the auto-created runtime execution role could not call Retrieve on my Knowledge Base or start browser sessions, and those calls failed with AccessDenied. I added least-privilege inline policies: bedrock:Retrieve scoped to my Knowledge Base ARN, and browser actions scoped to the AWS-managed aws.browser.v1 resource, whose ARN uses "aws" in place of an account ID.

**Production consideration.** Security is the biggest gap. The Gateway uses the NONE authorizer, so anyone with the URL could call initiate_refund. That is acceptable in a temporary sandbox but not in production. I would switch to a JWT authorizer (for example Amazon Cognito), take the customer ID from the verified token instead of trusting customer_id in the request payload, and check server-side that an order belongs to that customer before issuing a refund. For monitoring, I would add a CloudWatch metric filter on ERROR entries in the runtime log group, plus an alarm on Code Interpreter fallback usage, so a silently degraded calculator gets noticed.
